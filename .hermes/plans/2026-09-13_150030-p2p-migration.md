# Blaze P2P Migration Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Move Blaze from a centralized FastAPI/Neo4j application toward a local-first, signed-event, peer-to-peer architecture without breaking the existing prototype during migration.

**Architecture:** Introduce a transport-independent domain/event layer first, then add local persistence and projections, followed by browser synchronization over WebRTC. Keep FastAPI/Neo4j as an optional compatibility/community node until the peer protocol is mature. Treat the local replica and verified event log as the source of truth for the new client.

**Tech Stack:** Svelte 5, IndexedDB for browser-local state, SQLite for durable nodes, Web Crypto API initially, Python protocol/reference implementation, FastAPI signaling/compatibility services, WebRTC data channels, existing Neo4j derived projection.

---

## Current Context and Constraints

The current repository contains:

- `frontend/`: Svelte 5 + Vite + `svelte-spa-router`
- `backend/`: FastAPI routes backed by Neo4j
- `backend/app/auth/`: password hashing and HS256 JWT authentication
- `backend/app/database.py`: Neo4j as the required route-level database
- `backend/tests/`: centralized API and flow tests
- `README.md`: target architecture and decisions

Important constraints:

- Do not begin by deleting Neo4j, JWT, or existing API routes.
- Do not make WebRTC the source of truth; it is only a transport.
- Do not replicate mutable database rows directly.
- Do not introduce a full gossip mesh before two-peer synchronization is reliable.
- Do not claim mobile background-server capability; phones are opportunistic peers.
- Any cryptographic format must use vetted platform/library primitives and canonical encoding.

## Target Milestones

1. Protocol specification and domain boundary.
2. Deterministic signed events in Python and browser implementations.
3. Local event store and projections in the browser.
4. Local-first profile and post flows.
5. Compatibility bridge from existing API mutations to events.
6. WebRTC signaling and two-peer synchronization.
7. Event-backed social graph features.
8. Media, privacy, moderation, and provider infrastructure.
9. Native/mobile enhancements after protocol validation.

## Phase 9: Cutover and Deprecation

### Task 9.1: Define readiness gates

Before making local-first the default, require:

- Protocol test vectors passing in Python and browser.
- Projection rebuild equivalence.
- Duplicate/out-of-order/reconnect tests passing.
- Identity export/import tested.
- Existing centralized behavior preserved in compatibility mode.
- Two real devices tested over different networks.
- Privacy and deletion claims documented accurately.
- Backup/restore tested for event logs and identities.

### Task 9.2: Switch default mode gradually

Roll out in this order:

1. Centralized mode remains default.
2. Local identity and local read cache enabled for opt-in users.
3. Local-first posts/profile updates enabled for opt-in users.
4. P2P sync enabled for test communities.
5. Local-first becomes default while compatibility API remains available.
6. Legacy JWT/API mutations deprecated only after migration tooling and exports exist.

### Task 9.3: Deprecate central-only assumptions

Only after adoption evidence:

- Mark Neo4j as a derived/community-node projection.
- Remove route-level assumptions that every read requires Neo4j.
- Retain centralized API as an optional provider where useful.
- Remove password/JWT dependency only after explicit account/key migration and recovery are proven.

## Cross-Cutting Testing Strategy

Every protocol feature requires tests at four levels:

1. Unit: canonical encoding, signatures, validation, merge rules.
2. Property/fuzz: malformed events, size limits, arbitrary ordering, duplicates.
3. Projection: rebuild from raw events equals incremental projection.
4. Integration: two peers synchronize, disconnect, resume, and converge.

Required scenarios:

- Same event delivered repeatedly.
- Events delivered in reverse order.
- Missing parent arrives later.
- One peer has an incomplete replica.
- Signature is valid but authorization is invalid.
- Malicious peer sends oversized or high-volume input.
- Peer disconnects during a batch.
- Provider/signaling service is unavailable.
- Device exports and restores identity.
- Local content remains usable without a network.

Run the existing centralized suite throughout migration:

```bash
cd backend
python -m pytest tests/ --tb=short -v
cd ../frontend
npm run build
```

Add protocol-specific commands as they are introduced and require a clean result before each phase is considered complete.

## Risks and Tradeoffs

- Key recovery is harder than password reset and needs careful UX.
- Mobile background restrictions limit peer availability.
- Feeds and search may be incomplete on stale replicas.
- Replicated deletion is best-effort.
- Moderation becomes scoped and potentially inconsistent across communities.
- Peer-to-peer synchronization creates new spam and resource-exhaustion surfaces.
- End-to-end private group content requires key lifecycle and revocation design.
- A local event log can grow large and needs compaction/retention rules.
- Neo4j-derived views must not accidentally become an undeclared central authority.
- Browser cryptography and native cryptography must remain interoperable.

## Open Questions to Resolve Before Production

1. Which exact signature algorithm and canonical encoding will be standardized?
2. Will identities use raw public keys, DIDs, or another stable identifier format?
3. How are group encryption keys distributed and revoked?
4. What are the default event retention and local storage limits?
5. Which community moderation policies are opt-in versus mandatory for a provider?
6. How are camp/group roles recovered if the original organizer loses their key?
7. What data is searchable on third-party index nodes?
8. What is the minimum native capability needed for a Burning Man field deployment?
9. How will legacy server accounts be explicitly linked to new local identities?
10. What data must be available in local-only playa mode?

## Definition of Done for the First P2P Release

The first meaningful release does not need every feature. It must prove the architecture:

- A user can create or restore a local identity.
- A user can create a signed profile and post offline.
- A local event log survives reload and export/import.
- Two browsers can exchange and verify events over WebRTC.
- Peers converge after disconnect and reconnection.
- Feeds are built from local projections.
- Invalid, unauthorized, duplicate, and oversized events are handled safely.
- The current centralized prototype remains available as compatibility mode.
- Documentation accurately states what is and is not decentralized.
